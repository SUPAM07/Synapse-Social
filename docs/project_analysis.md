# EventManager – FAANG Resume Readiness Analysis

## Project Summary

**EventManager** is a full-stack event management platform with a microservices architecture. Users can discover events, register, download QR-coded PDF tickets, and post reviews. Organizers manage events, view participants, export CSVs, and perform real-time check-ins. Admins approve/reject events.

| Metric | Value |
|--------|-------|
| Total LOC (excluding deps) | ~6,400 |
| Services | 7 microservices + 1 gateway + 1 monolith backend + 1 frontend |
| Databases | MongoDB, PostgreSQL, Redis |
| Message Broker | Apache Kafka (6 topics) |
| Frontend | React 19 + Vite + Tailwind CSS |
| Real-time | Socket.IO |
| CI/CD | GitHub Actions (lint, build, Docker image push) |
| Containerization | Docker Compose (14 containers) |
| Tests | ❌ **Zero** |

## Detailed Scoring Breakdown

### 1. Architecture & System Design — 7/10 ✅ Strong

**What's Good:**
- Genuine microservices decomposition (Auth, Event, Booking, Review, Check-in, Notification, Analytics) — not a fake monolith with folders
- API Gateway pattern with proper proxy routing, rate limiting, optional JWT parsing
- Polyglot persistence with **justified** database choices (MongoDB for flexible documents, PostgreSQL for ACID bookings, Redis for caching)
- Event-driven async communication via Kafka with well-defined topic schema
- Shared library pattern (`@ems/shared`) for cross-cutting concerns (Kafka, Redis, logging, config)

**What a FAANG Interviewer Would Ask:**
- *"What happens when the Booking Service successfully books but the PATCH to Event Service to decrement seats fails?"* → You have no compensating transaction / saga pattern
- *"How do you handle Kafka consumer failures?"* → No dead-letter queue (DLQ) implementation, only mentioned in docs
- *"What's your service discovery strategy?"* → Hardcoded URLs, no service mesh or dynamic discovery
- *"How would you shard this beyond a single Kafka partition?"* → No partition key strategy visible

**Missing for FAANG-level:**
- No circuit breaker pattern (e.g., no `opossum` or retry with backoff on HTTP calls between services)
- No distributed tracing (no OpenTelemetry, no correlation IDs propagated between services)
- No saga pattern for distributed transactions (the booking flow is a fragile 2-phase process)
- Service-to-service auth is essentially nonexistent (if you hit the service directly, you bypass the gateway)

## Priority Improvements (Ranked by Impact)

### 🔴 Tier 1: Must Fix (blocks resume usage)

1. **Rewrite + own the code.** Squash the git history or better yet, rebuild the core pieces yourself from scratch. The Copilot commit trail is a deal-breaker. At minimum, squash all commits into meaningful, human-authored commits.

2. **Add tests immediately.**
   - Unit tests for each service controller (Jest/Vitest)
   - Integration tests for the booking flow (PostgreSQL testcontainers)
   - E2E test for registration → booking → check-in flow
   - Target: 60%+ coverage for critical paths

3. **Add TypeScript.** At minimum, convert the `shared/` library and one service (Booking is ideal since it's the most complex). Shows you understand type safety.

4. **Add input validation.** Use Zod or Joi on every endpoint. This is a 2-hour improvement that dramatically increases quality perception.

### 🟡 Tier 2: Should Fix (makes it competitive)

5. **Break up the frontend.** Split `Dashboard.jsx` into 5+ components. Add React Query for data fetching. Add loading states and error boundaries.

6. **Add distributed tracing.** OpenTelemetry with a correlation ID propagated through Kafka messages and HTTP headers. Shows you understand observability.

7. **Implement a saga for bookings.** When the seat decrement fails, compensate by cancelling the booking. This is a FAANG-favorite system design pattern.

8. **Add a circuit breaker.** Use `opossum` on the Booking→Event HTTP call. Shows resilience thinking.

9. **Clean up the monolith.** Remove `backend/` entirely or clearly mark it as "legacy" with a migration doc explaining the journey.

### 🟢 Tier 3: Nice to Have (makes it impressive)

10. **Add Kubernetes manifests.** Even a basic `kubectl apply` setup shows you understand container orchestration.

11. **Add monitoring.** Prometheus metrics endpoint per service + a simple Grafana dashboard.

12. **Write ADRs.** "Why Kafka over RabbitMQ?" "Why PostgreSQL for bookings?" — shows engineering judgment.

13. **Add a load test.** k6 or Artillery script showing the system handles 1K concurrent bookings without double-booking.
